## 三、关键结论

### ✅ 正面肯定（写进团队反馈）
1. **午夜时柱 bug 确已修**（前序审计 `h=0` 被 `||12` 吞掉）：`2000-01-01 00:30 → 壬子` 与 lunar-javascript 完全一致。
2. **时辰边界修正段正确**：真太阳时跨时辰时，用五鼠遁重算时柱天干，逻辑自洽（本次实证推翻"疑似时柱错配"的误报——属 false positive，与上轮时主星误报同型）。
3. **真太阳时正确应用**：乌鲁木齐 23:00 标准时 → 真太阳时 21:10 → 戌时（丙戌），抚远 23:00 → 真太阳时次日 00:05 → 次日日柱。经度补偿链路（`_setSel2s` + 边界修正）工作正常。

### ⚠️ 需文档化的流派边界（非 bug）
- **23:00 整点日柱归属**：bazi 引擎（`mingLiBaZi`）将 **23:00:00 整点算当日日柱、23:00:01 起算次日**（晚子时换日流派）；而 lunar-javascript 对 23:00 含即换次日。两者差 **1 分钟边界**，属流派定义差异，**不是计算错误**。
- 误报风险：用户用某 App 对比"23:00 整点排盘"，可能看到日柱差一天 → 易被误判为 bug。已在 `core/__tests__/boundary.test.js` 固化断言（`庚戌`/`辛亥`），并在 `bazi-cross-verify` skill 的已知 bug表加注，**禁止"修正"**。

## 五、给团队的两条核心教训

1. **交叉验证前先读权威引擎真实输出，勿凭编码推演下结论**。本轮"时柱错配"的担忧源于对 `mingLiBaZi` 日界（误判为 01:00）的静态推演；实测是 23:00 换日流派。没有三引擎实证，极易误修。
2. **流派边界要文档化，不要"统一"**。八字排盘的晚子时、真太阳时、闰月等存在多流派，强行"和某库一致"会引入错误。用测试固化本项目的流派选择，比争论"谁对"更有价值。
