> 资深开发工程师带教记录 · 2026-07-15
> 背景：团队提升闭环的最后一环。本专题在实操中暴露了一个**由我自己引入、且被我自己测试网住的回归 bug**，

## 一、为什么八字必须算「真太阳时」

平太阳时（钟表时）是人为均匀化的时间；真太阳时是太阳真实视位置对应的时间。
同一钟表时刻，不同经度的真太阳时不同——东边先见日。八字以「太阳真位置」定时刻，
若直接用北京时间排盘，东西跨度大的出生地会系统性偏错时辰。

本产品经度参数 `jd`（°E，东经为正）即为此而设，默认 116.4（北京）。

---

## 二、核心公式

```
真太阳时 = 标准时 + (λ/15 − TZ)×60 分钟 + EoT(均时差)
```

- `λ`：出生地经度（°E，东正西负）
- `TZ`：时区（北京 = 8）
- `EoT`：均时差（太阳视运动与平运动之差，全年 ±16 分钟）

### 均时差 EoT（Meeus 简化式，分钟）

```
N  = 一年中的第几天（1-365/366）
B  = (360/365)·(N−81)·π/180
EoT = 9.87·sin(2B) − 7.53·cos(B) − 1.5·sin(B)      // 分钟
```

### 验证（与活服务对拍）

- 北京 λ=116.4，TZ=8 → `(116.4/15 − 8) = −0.24 h = −14.4 min`
- 2000-01-01 08:55 标准时 → 真太阳时 ≈ `08:55 − 14.4 − ~3(EoT) ≈ 08:37`
- 活服务返回 `08:36:54`（见 `verify/_bazi_minute_e2e.mjs`）：**实测与公式一致** ✅

## 三、本产品实现链路

```
前端表单(Cml_his "HH:MM")
  → web/js/time-util.js parseClockTime / normalizeHour / normalizeMinute   [ESM 共享]
  → POST /api/v1/bazi  { h, min, jd, wd }
  → server/routes/bazi.js
       h   = timeUtil.normalizeHour(body.h, 12)    // 保留 h=0（午夜/早子时）
       min = timeUtil.normalizeMinute(body.min, 0) // 保留 min=0，且 24-59 合法
       d0  = JD.JD(y,m,d + (h+min/60)/24) − J2000
       Lunar.mingLiBaZi(d0, jd·π/180, ob, ...)     // 引擎本体
  → 引擎 bz_zty（内部 EoT 符号相反 + 78s 历史兼容，有偏差）
  → bazi.js 用 Meeus 公式「重算并覆写」bz_zty（权威真太阳时）
```

**关键架构点**：引擎内部 `mingLiBaZi` 的 EoT 符号与权威相反且带 78s 历史兼容修正，
故 `bazi.js` 不信任引擎的 `bz_zty`，而是用 Meeus 重算后覆写。这是「引擎有偏差→上层覆写」模式。

## 四、坑位清单（按严重度）

### 🔴 坑 2【本次实战，最高优先级】— 自引入 time-util 回归：分钟被钳成 0

**现象**：把时辰解析抽成 `time-util.js`（红线 9 收口）时，后端 `bazi.js` 写了
`min = timeUtil.normalizeHour(body.min, 0)`。而 `normalizeHour` 对 `n>23` 钳制到兜底值——
**分钟 24-59 全部被静默归零**。

**影响面**：所有分钟在 24-59 的出生时间（约 60% 真实出生时刻）分钟算错。
时柱按传统 2 小时柱划分（辰=7:00-9:00），分钟内不跨柱，所以**时柱/日柱看不出异常**，
只有真太阳时（分钟敏感字段）能暴露。

**根因**：小时(0-23)与分钟(0-59)是**不同取值域**，误用同一 `normalizeHour` 解析分钟。

**修复**：新增 `normalizeMinute(min, fallback=0)`（域 0-59），后端改用它；ESM 镜像同步。
`verify/_time_util_audit.mjs` 已加 24-59 区间断言，`verify/_bazi_minute_e2e.mjs` 端到端锁死。

> ⚠️ **这条 bug 是我上一轮「自己抽工具、自己写测试」引入并漏网的**——见第五节教训。

### 🟠 坑 1 — 晚子时 / 午夜日界（历史，已闭环）

`23:00-23:59` 在子平流派属「晚子时」，部分流派当日换日、部分次日换日。
`bazi.js` 用 `isNaN(h)?12:h` 守卫保留 `h=0`（午夜合法值），杜绝 `parseInt||12` 把 `00:xx` 误判正午。
已在 `core/__tests__/boundary.test.js` 固化。

### 🟡 坑 3 — 引擎 EoT 符号 / 78s 历史兼容

`mingLiBaZi` 内部 `bz_zty` 与权威偏差，`bazi.js` 用 Meeus 覆写。上层不要直接信任引擎 `bz_zty`。

## 五、测试纪律（本次最大教训）

> 我自己的共享工具引入了系统性回归，而我自己的测试**完美漏网**。复盘根因：

1. **测实际取值区间，不要假设对称**。
   单测只覆盖了 `0-23`（小时）的 `normalizeHour`，从没测 `min > 23`。
   分钟的取值域是 `0-59`，`24-59` 才是高频真值域——测试却只覆盖了低频边界。

2. **e2e 断言要打到「会变的字段」**。
   午夜 e2e 用了 `min:30`，被静默钳成 0，但断言只查时柱（不随分钟内变化）→ 假绿。
   正确做法：断言分钟敏感字段（真太阳时），且用 `min:55` 这类真实高频值。

3. **不要凭推理下 bug 结论，要用探针对照真值**。
   本次调查一度误判「日柱跨日 gap」是真 bug（因探针用了 min=55 而活服务收到 min=0，差异全来自分钟 bug）。
   引擎本身日界处理是对的。凡是「看起来像 bug」都要先排除上游污染（陈旧进程、分钟钳制等）。

4. **改共享工具 = 改所有调用点，必须全量回归**。
   抽 `time-util` 后，三处调用点（app.js / bazi-ui.js / bazi.js）语义必须一致；
   任何一处误用都会系统性出错，CI 必须覆盖所有调用点的真实取值域。
