# 公信万年历 — 前后端分离架构设计文档

**版本**: v1.0  
**日期**: 2026-06-17  
**状态**: 待审阅

## 一、背景与目标

### 现状

公信万年历当前为单文件 HTML 应用（~17127 行），纯 JavaScript（ES5 兼容）+ lunisolar 天文历算库（CDN importmap），通过 WebView 封装为 Android APK 交付。

### 痛点

| 问题 | 影响 |
|------|------|
| 单文件过大（17127行） | 改一个功能需在巨型文件中定位，牵一发动全身 |
| 计算逻辑与UI混杂 | 改CSS可能搞崩八字算法，无法独立测试 |
| 核心算法暴露在前端 | 源码中可直接查看全部计算逻辑 |
| 无法多端复用 | Web/Android/iOS/小程序各自拷贝完整HTML |
| 首屏全量加载 | 低端手机解析执行慢（2-3秒白屏） |
| 团队协作困难 | 多人改同一文件，冲突频繁 |

### 目标

将单文件拆分为 **共享计算库（core）+ API 后端（server）+ 多前端（web/android/未来）** 三层架构，实现：

1. 核心算法保护（后端计算，前端只调API）
2. 模块独立维护（每个模块 <500行，改A不影响B）
3. 多端统一消费（一套API，Web/PWA/APK/小程序复用）
4. 按需加载（首屏0.5秒，其他模块懒加载）
5. 离线可用（Service Worker + 裁剪版本地引擎）

---

## 二、技术选型

| 层 | 技术 | 理由 |
|----|------|------|
| **共享计算库** | Node.js npm 本地包 | 现有代码零改写，直接提取 |
| **API 后端** | Node.js + Express | 与 core 同语言，零翻译成本 |
| **Web 前端** | 原生 JS + ES Modules + Vite | 学习成本零，打包体积最小，WebView兼容最好 |
| **CDN/防护** | Cloudflare | DDoS防护 + Bot检测 + 免费计划 |
| **部署** | 阿里云 ECS + OSS | 国内访问快，Cloudflare前置 |
| **移动端** | WebView APK + PWA 双模 | 安卓走APK（可靠），iOS/桌面走PWA |

### 不采用的方案

| 方案 | 原因 |
|------|------|
| Next.js SSR | 学习曲线陡，与原生JS选型冲突 |
| Python 后端 | 需翻译4000+行JS计算逻辑，易引入bug |
| React/Vue | 增加框架依赖，WebView兼容性风险 |
| 微服务 | 过度设计，单人项目不需要 |

## 四、Core 共享计算库

### 模块划分

```

├── package.json
├── index.js          ← 统一导出（Node require / 浏览器 import 双环境）

├── shensha.js        ← 神煞, 二十八宿, 建除十二神, 宜忌推算 (~600行)
```

### 迁移规则

1. **零破坏**：所有函数签名保持不变，全局常量转为模块导出

3. **lunisolar 依赖**：服务端使用 npm 包 `lunisolar@2.6.0` + `@lunisolar/plugin-thegods`
4. **每模块迁移完立即跑单元测试**

## 五、后端 API 设计

### 技术栈

```
Node.js + Express
lunisolar npm 包（替代 CDN importmap）
无数据库（纯计算服务，无状态）
```

### 路由表

所有路由前缀 `/api/v1`，统一返回 `{ ok, data, took }` 或 `{ ok, error, code }`。

| 方法 | 路由 | 说明 |
|------|------|------|
| POST | `/api/v1/bazi` | 八字排盘全量（排盘+从格+喜用+详断+神煞+称骨） |
| POST | `/api/v1/bazi/congge` | 从格分析（单独调用） |
| POST | `/api/v1/bazi/xiyong` | 喜用神判定（单独调用） |
| POST | `/api/v1/bazi/sizhu` | 四柱动态详断（单独调用） |
| POST | `/api/v1/calendar/month` | 单月日历数据（含宜忌/神煞/建除/二十八宿） |
| POST | `/api/v1/calendar/day` | 单日完整详情（含时辰黄黑道/九星网格） |
| POST | `/api/v1/calendar/nianli` | 整年年历数据 |
| GET | `/api/v1/health` | 健康检查 |

### 分步调用说明

- `/bazi` 一键返回全量（推荐）
- `congge`/`xiyong`/`sizhu` 用于从格/喜用/四柱面板独立刷新，避免重复计算
- 八字分步接口复用 `core/bazi.js` 中对应函数，不重复实现

### 缓存策略

| 数据类型 | Cache-Control | 说明 |
|---------|---------------|------|
| 日历月数据 | `max-age=3600` | 公众数据，可CDN |
| 八字结果 | `no-store` | 含个人信息，不缓存 |
| 静态资源 | `max-age=604800` | CSS/JS/图标 7天 |

### 模块隔离规则

#### 铁律：UI 模块间零直接依赖

```
✅ 允许的依赖                    ❌ 禁止的依赖
─────────────                   ─────────────
bazi-ui → api.js                bazi-ui → calendar-ui.js
bazi-ui → state.js              calendar-ui → bazi-ui.js
bazi-ui → dom-helpers.js        detail-ui → note-ui.js
任何UI模块 → core/lite.js       任何 UI 模块 → 另一个 UI 模块
```

#### 每个模块标准结构

```javascript
// bazi-ui.js — 八字排盘模块
// 依赖：api.js, state.js, dom-helpers.js
// 公开：BaziUI.init(containerEl), BaziUI.destroy()
// 发布事件：bazi:done, bazi:clear
// 订阅事件：state.listen('date:selected', handler)

const BaziUI = (function() {
  // 私有状态
  let _container = null;

  // 公开接口
  function init(el) { /* 绑定事件 */ }
  function destroy() { /* 清理DOM和事件 */ }

  return { init, destroy };
})();
```

#### 模块清单与事件契约

| 模块 | 发布的事件 | 订阅的事件 |
|------|-----------|-----------|
| `calendar-ui.js` | `date:selected`, `month:changed` | `settings:changed` |
| `detail-ui.js` | — | `date:selected`, `settings:changed` |
| `bazi-ui.js` | `bazi:done`, `bazi:clear` | `date:selected` |
| `note-ui.js` | `note:saved` | `date:selected` |
| `settings-ui.js` | `settings:changed`, `theme:toggled` | — |
| `archive-ui.js` | — | `bazi:done` |
| `license-ui.js` | `license:activated` | — |

#### 错误隔离

每个模块 `init()` 包裹 try-catch，一个模块崩溃不影响其他：

```javascript
const MODULES = [
  { name: 'calendar', init: () => CalendarUI.init('#cal-root') },
  { name: 'bazi',     init: () => BaziUI.init('#bazi-root') },
  // ...
];

MODULES.forEach(mod => {
  try { mod.init(); console.log('[boot] ' + mod.name + ' ✓'); }
  catch(e) { console.error('[boot] ' + mod.name + ' FAILED', e); }
});
```

### 离线策略


### 单文件 vs 新架构 加载对比

```
旧：加载 index.html (740KB → gzip ~180KB)
    → 解析全部 17127 行 → 执行全部 script
    → Time to Interactive: ~2-3秒（低端手机）

新：加载 index.html (~5KB)
    → 并行加载 calendar-ui.js (~25KB) + calendar.css (~10KB)
    → 调 API /calendar/month → ~100ms
    → Time to Interactive: ~0.5秒
    → 其他模块(bazi/settings/archive) 按需懒加载
```

## 七、安全防护

### 五层防护

| 层 | 措施 | 拦截能力 |
|----|------|---------|
| 1 | **Cloudflare** CDN + DDoS + Bot检测 + JS Challenge | 自动化攻击 90% |
| 2 | **HSTS** `max-age=63072000` | 中间人攻击 |
| 3 | **HMAC 请求签名**（时间戳 + nonce + 机器码） | 直接调API、脚本伪造 |
| 4 | **IP 限流** 60次/分钟（Express中间件） | 批量爬虫 |
| 5 | **CORS 白名单**（仅允许自家域名） | 跨站调用 |

### HMAC 签名方案（复用现有授权体系）

```
客户端每个请求：
  timestamp = Date.now()
  nonce = randomHex(8)
  mid = 机器码（现有 license_simpleHash）
  signature = HMAC-SHA256(mid + timestamp + nonce + path, HMAC_KEY)

请求头：
  X-Machine-Id: A1B2C3D4E5F6
  X-Timestamp: 1718572800000
  X-Nonce: a3f7b2c1
  X-Signature: 8a3c...
```

### 服务端验证流程

```
1. 检查 timestamp 在 ±5 分钟内（防重放）
2. 检查 nonce 未使用过（内存 LRU，防重放）
3. 重新计算签名 → 比对
4. 失败 → 401，静默拒绝
```
